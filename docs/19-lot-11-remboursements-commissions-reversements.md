# Lot 11 — remboursements, commissions et reversements

Statut : livré, à recetter. Aucune valeur commerciale n'est approuvée par ce lot : le taux de commission (10 %), le seuil de double validation (100 000 FCFA) et la répartition des frais du prestataire sont des **propositions de travail non validées**, configurables, jamais appliquées rétroactivement. Rien n'a été exécuté en réel ; le mode de paiement configuré n'a pas été touché.

## 1. Principe : décision ≠ opération ≠ exécution
Une décision du support (« remboursement », « répartition », « reversement à autoriser ») **ne rembourse ni ne verse rien**. Une **opération financière** (`financial_operations`) est *demandée* par un administrateur, *approuvée* par d'**autres** personnes, puis *exécutée*. États : demandé, approuvé, en cours, confirmé, échoué, à vérifier (+ refusé, annulé). Un état n'est jamais présenté comme « effectué » avant « confirmé » ; une réponse incertaine donne « à vérifier ». Réservé aux **administrateurs** (MFA, adresse vérifiée ; confirmation récente d'identité sur chaque route d'écriture ; journal d'audit). Le catalogue d'habilitations (Q07) n'étant pas décidé, aucune habilitation « finance » n'est créée : seuls les administrateurs agissent (le support décide, il ne touche pas aux tables financières).

## 3. Registre et conditions financières
- **Accord** : `order_agreements.commission_bp` et `commission_policy` figés **à la création de l'accord** (demande de service ou sélection de proposition). Les accords existants restent **nuls** : leurs conditions financières sont **insuffisantes** → aucun reversement éligible, montant non calculé, signalé à l'écran (aucun taux inventé). Les accords restent immuables (déclencheur existant).
- **Calcul** (`FinancialPolicy`, entiers FCFA) : commission = `(base × bp + 5 000) ÷ 10 000` (division entière : arrondi au franc le plus proche, demi vers le haut) ; part du freelance = base − commission (la somme est toujours exacte). **Base = encaissement − remboursements confirmés ou réservés** (cas de l'architecture : 100 000 − 20 000 → 8 000 / 72 000 ; − 40 000 → 6 000 / 54 000).
- **Comptes du registre existant** (suffixe `_simulated` pour tout ce qui vient du mode test) : `external_payer` (payé par le client), `escrow` (encaissé, non engagé), `refund_reserved`, `platform_commission`, `payout_reserved`, `external_freelancer` (effectivement reversé). Lots équilibrés, en ajout seul, un lot par `event_key` :
  - paiement confirmé : `external_payer −P`, `escrow +P` (existant) ;
  - remboursement demandé : `escrow −A`, `refund_reserved +A` ; confirmé : `refund_reserved −A`, `external_payer +A` ;
  - reversement demandé (allocation + réservation) : `escrow −base`, `platform_commission +C`, `payout_reserved +D` ; confirmé : `payout_reserved −D`, `external_freelancer +D`.
- **Corrections** : jamais d'UPDATE ni de DELETE. Un refus, une annulation ou un échec libère la réservation par une **écriture correctrice** liée au lot corrigé (`reverses_batch_id`, une seule correction par lot).
- **Fonds engagés une seule fois** : verrou de commande, plafond calculé depuis le registre, **et** contrainte différée en base : le solde `escrow` d'une commande ne peut jamais être négatif. Un remboursement et un reversement ne peuvent donc pas consommer les mêmes fonds.
- **Frais du prestataire** : informatifs (voir §2). **Commission acquise** = commission des reversements **confirmés** (une réservation n'est pas un revenu).

## 4. Remboursements (parcours)
1. Décision du support avec suite « remboursement » ou « répartition ». 2. Un administrateur **demande** l'opération (montant vide = total ; plafond = fonds non engagés ; une seule opération ouverte par paiement ; un seul remboursement total vivant). Les fonds sont **réservés**. 3. **Approbation** par une autre personne (jamais le demandeur, jamais une partie à la commande) ; au-delà du **seuil configurable** (`FREECI_FINANCE_DUAL_APPROVAL_XOF`, **non validé**), deux approbateurs distincts. L'approbation porte sur l'**empreinte** de l'action exacte (type, commande, paiement, montant, bénéficiaire, environnement) ; les caractéristiques d'une opération sont **immuables** (déclencheur), donc toute modification exige une nouvelle opération. 4. **Exécution par API (total)** : référence sortante enregistrée **avant** l'appel ; `approved → in_progress` conditionnel ; appel hors transaction ; résultat : *confirmé* (corps cohérent), *échoué* (refus définitif : clés, validation, transaction inconnue — réservation libérée), *à vérifier* (délai dépassé, 5xx, 409, corps incohérent, envoi interrompu). 5. **Aucun renvoi automatique, jamais** : `freeci:finance:reconcile` (toutes les 5 min) **lit** le paiement ; « refunded » ⇒ confirmé. Pour un envoi incertain, l'administrateur peut *reprendre* (nouvel envoi, idempotent chez le prestataire) ou *constater l'échec* **uniquement après une lecture fraîche** montrant le paiement toujours « complété » ; si la lecture est indéterminée, rien n'est possible.
Une opération de remboursement confirmée lève le blocage interne du dossier décidé (le reversement du solde peut alors suivre) ; les décisions « à traiter financièrement » disparaissent de la liste quand une opération confirmée leur est rattachée.

## 5. Reversements
- **Éligibilité calculée** (`PayoutEligibility`), jamais stockée comme un versement : paiement Genius Pay confirmé ; conditions financières figées ; **validation explicite** (clôture « validée ») **ou** décision motivée du support (reversement à autoriser / partiel) — **le silence du client n'ouvre jamais rien** ; aucun litige ni blocage interne ; aucun dossier de rapprochement ouvert ; **bénéficiaire vérifié et actif** ; aucun reversement concurrent ; aucun remboursement ouvert ; fonds disponibles ; part non nulle. Recalculée **sous le verrou de commande** à la demande, et le blocage est revérifié à l'approbation et à l'enregistrement.
- **Bénéficiaire** : déclaré par le freelance (destination **chiffrée**, jamais réaffichée), **vérifié** par un administrateur (jamais par son titulaire) ; une modification crée une nouvelle déclaration à vérifier. La procédure de vérification elle-même n'est pas définie ici.
- **Exécution : manuelle uniquement** (rien n'est documenté). L'administrateur enregistre un transfert **déjà effectué** avec **référence externe unique**, **justificatif**, **montant retapé** et **case de confirmation explicite** ; l'auteur est conservé ; l'opération passe « confirmée » seulement à ce moment (même transaction que l'écriture du registre). Les écrans affichent « exécution via Genius Pay indisponible ». Aucun reversement n'est simulé.
- `PayoutExecution::executed()` (contrat du lot 9) : vrai seulement si un reversement est **confirmé**, ou en cours / à vérifier chez un prestataire. Une demande ou une approbation n'est pas une exécution : un litige peut encore bloquer.

## 6. Interfaces
- **Administration** `/admin/finances` : totaux **réel / test séparés**, opérations à approuver, ouvertes, décisions à traiter (avec plafond), commandes validées (éligibles ou non, motifs), destinations à vérifier, historique ; détail `/admin/finances/operations/{réf}` (décomposition, approbations, registre, historique, actions). Tableau de bord : opérations à approuver / à vérifier.
- **Client** `/espace/finances` et onglet « Finances » de la commande : payé, remboursé, états des remboursements (libellés prudents).
- **Freelance** `/freelance/revenus` : à venir, bloqué, disponible, reversement en cours, reversé — **réel et test séparés** (un montant de test n'est jamais un revenu) ; destination ; mention de l'exécution API indisponible. Les anciennes commandes sans taux figé : « conditions financières non figées », sans montant inventé.
